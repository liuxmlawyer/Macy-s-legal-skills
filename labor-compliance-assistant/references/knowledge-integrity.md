# 知识层防错与同步机制

> **本文件是整个技能的自省机制。**
>
> 本技能的知识层（`dismissal-pathway.md` / `evidence-checklist.md`）是**基于经验与学习材料的人工总结**，
> 不是法条原文。因此它**天然存在出错可能**——条号记错、要件概括偏差、口径过时、地区差异遗漏。
>
> 本文件规定：如何让这些错误**能被系统自己发现**，并在发现时**提示用户更新**。

---

## 序、核心认知：知识层不是权威，是"待核验的经验"

| 常见误解 | 正确认知 |
|---|---|
| 技能里写了第40条三步法，照着做就对了 | 知识层是**经验归纳**，可能概括不准，**法条原文才是准的** |
| 内容既然写进技能了，就不用再查法 | 写进去只代表**曾经核验过**，不代表**现在仍然有效** |
| 模型引用知识层就是"有依据" | 引用自己的总结**不构成依据**，那是自证循环 |
| 知识层永远不用改 | 法条会变、口径会变，**知识层必须带版本与核验日期** |

> ⚠️ **一句话铁律**：
> **知识层只能用于"指引方向"，不能用于"支撑结论"。凡是要下确定性结论，必须回权威源取法条原文。**

---

## 一、三层信任分级（防自指循环的核心）

技能里同时存在三种"知识"，它们的可靠性**完全不同**，必须分开对待：

| 层级 | 名称 | 具体是什么 | 可否支撑确定性结论 | 校验要求 |
|---|---|---|---|---|
| **A1** | **权威源** | flk-npc 国家法律法规数据库、北大法宝的**法条原文与生效文本** | ✅ 可以 | 取原文即可 |
| **E1** | **技能实体层** | `dismissal-pathway.md`、`evidence-checklist.md` —— **本技能自己写的经验总结** | ❌ **不可以** | **必须回 A1 校验法条** |
| **E2** | **企业知识库** | `user-knowledge/` 下的企业制度、SOP、历史结论 | ❌ **不可以** | 必须回 A1 校验，且受法律约束 |

### 1.1 为什么 E1 不能支撑结论

```
错误链条（必须避免）：

  技能写了"三步法"
      ↓ 引用
  报告写"依据：技能实体层第40条三步法"
      ↓
  结论：不能胜任解除路径合规
      ↓
  ❌ 这叫自证循环——用自己写的总结证明自己写的东西对
```

**正确链条**：

```
  技能写了"三步法"（经验，指引方向）
      ↓ 触发
  回 A1 取《劳动合同法》第40条原文
      ↓
  核对：原文是否确实是"培训或调岗 → 再次考核 → 仍不能胜任可解除"
      ↓
  ✅ 结论建立在法条原文上，技能的总结只是检索线索
```

### 1.2 E1 层的正确用法

| ✅ 可以 | ❌ 不可以 |
|---|---|
| 作为**检索线索**去查法条（"第40条不能胜任"） | 直接当依据写进报告 |
| 作为**分析框架**组织问题（先排第42条→五步排除法） | 用来替代法条原文核验 |
| 作为**风险提示**告诉用户"这里容易踩坑" | 用"技能手册说"作为说服用户的理由 |
| 作为**证据清单模板**帮 HR 自查 | 在报告"依据"栏写"解聘手册V4" |

> 📌 **报告"依据"栏的硬规定**：
> 只能写**法规名称+条号+文号+效力状态**。
> **禁止**出现"技能手册""实体层""解聘手册V4""经验总结"作为法律依据。

## 二、四类失效场景（知识层会怎么错）

### 场景一：法条已修订，条号变了

- **典型**：劳动争议司法解释迭代替换，条号重新编排
- **检测**：每次引用前核对 A1 源的**文号 + 施行日期 + 效力状态**
- **触发条件**：`staleness-trigger` 命中 `judicial-interpretation-updated`

### 场景二：要件概括偏差

- **典型**：技能写"三步法"，但法条原文其实是"经培训或者调整工作岗位"——**"或者"的关系被写成"且"**，导致实操中以为两者都要做
- **检测**：把技能写的步骤**逐项回原文比对**，看有无增删、关系词改变、条件遗漏
- **触发条件**：`staleness-trigger` 命中 `statute-amended`

### 场景三：地区口径过时

- **典型**：某地高院会议纪要已废止或被新纪要替代
- **检测**：地区口径**每次都必须实时检索**，知识层中的地区表仅作提示
- **触发条件**：`staleness-trigger` 命中 `regional-guideline-updated`

### 场景四：知识层内部自相矛盾

- **典型**：`dismissal-pathway.md` 说"三期不可解"，但另一处说"有第39条过错可解"（实际两者都对，但表述容易冲突）
- **检测**：同一议题在不同文件表述不一致时，**以 A1 源为准**，并标记知识层待修订
- **触发条件**：`staleness-trigger` 命中 `internal-contradiction`

## 三、元数据头（每个知识层文件都要有）

### 3.1 标准格式

```yaml
---
layer: E1                          # 信任层级，必填（本地文件只能是 E1 或 E2）
file: dismissal-pathway.md          # 文件名
basis: 《劳动用工—员工解聘手册（增强修订版 V4）》  # 依据来源
basis-version: V4 / 2026-09        # 依据版本
verified-against:                   # 已回 A1 核验的法条范围
  - 《劳动合同法》第39条、第40条、第41条、第42条、第43条
  - 《劳动争议司法解释（二）》(法释〔2025〕12号)
last-checked: 2026-10-14           # 上次核验日期（YYYY-MM-DD）
confidence: high                    # high / medium / draft（三选一）
staleness-trigger:                 # 什么情况下本文件失效
  - statute-amended                 # 劳动法律法规修订
  - judicial-interpretation-updated # 劳动争议司法解释更新
  - regional-guideline-updated     # 地区口径文件更新
owner: Macy                         # 维护责任人
---
```

> ⚠️ **枚举值必须合法**：`layer` 只能取 `E1` / `E2`，
> `confidence` 只能取 `high` / `medium` / `draft`。
> 本地文件**不得自称 A1**——A1 指权威源原文，本地经验总结自称 A1 会形成自证循环。
> `last-checked` 必须是可解析的 `YYYY-MM-DD`，且**不得晚于今日**；
> 非法取值与日期会被 `knowledge_sync_check.py` 判为**阻塞项**。

### 3.2 confidence 三档的含义

| 档位 | 含义 | 使用要求 |
|---|---|---|
| **high** | 已逐条回 A1 源核验过，条号、要件、效力状态均确认 | 可作检索线索使用，**结论仍需 A1 支撑** |
| **medium** | 部分核验，或含地区口径等需动态确认的内容 | 引用时**必须提示用户该部分未完全核验** |
| **draft** | 经验总结为主，**尚未系统核验** | **引用即触发强制核验**，报告须披露"知识层未完成核验" |

> ⚠️ **confidence 不是免责符**。任何档位下，确定性结论都必须有 A1 源支撑。
> confidence 的作用是：告诉使用者"**这里该多信一点还是少信一点**"。

### 3.3 staleness-trigger 的作用

触发条件**命中即视为该文件内容不可直接采信**，必须重新核验。

在 SKILL.md 主流程中，**每次任务开始前**检查涉及文件的 `staleness-trigger` 是否命中。

## 四、冲突处置流程（发现错误时怎么办）

```text
发现知识层与 A1 源不一致
        ↓
① 立即停止使用该条知识层内容
        ↓
② 以 A1 源（法条原文）为准，作为报告依据
        ↓
③ 记录差异：知识层写的 vs 权威源实际写的
        ↓
④ 在报告「待确认/差异」区披露该差异
        ↓
⑤ 标记该知识层条目为"待修订"，写入同步待办
        ↓
⑥ 提示用户：建议更新知识层文件（给出具体改法建议）
        ↓
⑦ 用户确认后，修订知识层文件 + 更新元数据头
        ↓
⑧ 运行 knowledge_sync_check.py 确认同步完成
```

### 4.1 差异记录格式

发现差异时，写入工作底稿：

| 字段 | 内容 |
|---|---|
| 位置 | `dismissal-pathway.md` §5.4 第一步 |
| 知识层原文 | "三步法：培训 → 复考 → 解除" |
| 权威源原文 | 《劳动合同法》第40条第2项："经培训或者调整工作岗位，仍不能胜任工作的" |
| 差异性质 | **关系词错误**："培训或调岗"被写成两者都需做 |
| 影响 | 实操中可能漏做调岗路径选择，或误以为必须两项都做 |
| 处置 | 以权威源为准；建议修订知识层 |
| 状态 | ⏳ 待用户确认修订 |

### 4.2 提示用户的措辞

**不要**说："你的手册错了。"
**要说**：

> ⚠️ **知识层待更新提示**
>
> 核验过程中发现 `dismissal-pathway.md` §5.4 的表述与现行《劳动合同法》第40条第2项存在差异：
> - 知识层表述：三步法（培训 → 复考 → 解除）
> - 法条原文：经**培训或者**调整工作岗位，仍不能胜任的
>
> 本次分析已以**法条原文**为准，不影响结论。
> 建议您更新知识层该节，具体改法见下方建议。
> 是否需要我协助修改？

## 五、同步机制（知识层更新后，如何同步 Skill）

### 5.1 双向同步关系

```text
外部变化（法条修订/口径更新）
        ↓
知识层需要更新 ←──────────────┐
        ↓                      │
Skill 的 SKILL.md 元数据需更新   │ 用户更新知识层
        ↓                      │
工作底稿需重新核验              │
        ↓                      │
报告结论刷新 ────────────────────┘
```

### 5.2 四种同步触发场景

| 触发 | 症状 | 动作 |
|---|---|---|
| **T1 外部法律变化** | **检索时**发现法规修订/解释更新/口径变化 | 更新对应知识层条目 → 跑元数据体检 → 更新 SKILL.md 元数据 |
| **T2 检索中发现错误** | 报告待确认区出现差异记录 | 按 §4 处置 → 修订知识层 → 跑元数据体检 |
| **T3 用户主动更新** | 用户替换手册/SOP/法律材料 | 检查知识层是否需跟进 → 跑元数据体检 → 提示 Skill 是否需同步 |
| **T4 定期体检** | 距 `last-checked` 超过设定周期 | 跑元数据体检 → 输出体检报告 → 标记待复核条目 |

> ⚠️ **T1 的发现依赖"检索"，不依赖脚本。**
> `knowledge_sync_check.py` **不联网、不比对法条正文、不能自动发现法律修订**——
> 它能查出"你没更新日期/置信度"，查不出"法律变了"。
> **法律变化的唯一发现路径**，是在按 `kb-search-protocol.md` 回权威源核验时，
> 发现权威源文本与知识层表述不一致（走 §4 处置流程）。

### 5.3 同步检查清单（每次更新后执行）

```markdown
- [ ] 确认知识层修改了哪些文件（看 git diff 或文件时间戳）
- [ ] 运行 knowledge_sync_check.py，确认无"待核验"残留（**注意：该脚本只查元数据**）
- [ ] 检查被修改文件的元数据头是否同步更新（last-checked / confidence）
- [ ] 检查是否有其他知识层文件引用了被改内容（交叉引用一致性）
- [ ] 检查 SKILL.md 中对被改文件的描述是否仍准确
- [ ] 检查工作底稿中是否有基于旧版本的未结结论
- [ ] 通知用户：本次同步涉及的文件清单与影响范围
```

> 🔴 **元数据自洽 ≠ 内容正确**：第 2 步只能发现"元数据没跟上"，
> 发现不了"法条已被修订"。后者只能靠**重新回权威源核验**。

### 5.4 交叉引用一致性检查

知识层文件之间存在交叉引用，改一处可能影响另一处：

| 知识层条目 | 交叉引用位置 |
|---|---|
| 第42条六项情形 | `dismissal-pathway.md` §零、`evidence-checklist.md` §四、`risk-grading.md` |
| 经济补偿 3 倍封顶 | `dismissal-pathway.md` §三、`kb-search-protocol.md` §五、`evidence-checklist.md` §5.1 |
| 不能胜任三步法 | `dismissal-pathway.md` §5.4、`evidence-checklist.md` §二/§三、`risk-grading.md` |
| 同名多版本警示 | `kb-search-protocol.md` §四、`labor-law-registry.md`、`public-source-policy.md` |

> 📌 **改知识层时必须检查这张表**——改了 A 处，B/C/D 处不同步就会自相矛盾。

## 六、使用者视角：怎么知道知识层可不可信

### 6.1 交付报告时的知识层状态披露

每份报告的「待确认/差异」区**必须**披露：

```markdown
### 知识层核验状态

- 本次引用知识层文件：dismissal-pathway.md（confidence: high，核验于 2026-10-14）
- 已回权威源核验的法条：第39/40/41/42/43条
- **发现的差异**：2 处（见下）
- **未核验项**：地区口径（北京/上海/深圳/四川）依赖实时检索，本次未涉及具体地区
- **结论可靠性**：本次确定性结论均建立在 A1 权威源之上，知识层仅作分析框架
```

### 6.2 用户主动查询知识层状态

用户可以问："你的知识层现在可信吗？"

技能应回答：
1. 各知识层文件的 confidence 档位与 last-checked 日期
2. 是否有命中 staleness-trigger 的文件
3. 已知未修复的差异清单
4. 建议优先复核的条目

## 七、边界声明

1. 本机制**降低**知识层出错概率，但**不能消除**。法条原文仍是唯一可靠依据。
2. `confidence: high` **不等于**绝对正确，只表示"曾核验过且近期未触发失效条件"。
3. 知识层与权威源冲突时，**永远以权威源为准**，知识层服从法条。
4. 用户可以不同意同步建议，**但技能必须披露该差异的存在**——不披露比错误本身更危险。
5. 本机制不替代律师审核，尤其高风险定性（违法解除、三期解除、社保欠缴）**必须升级人工确认**。
